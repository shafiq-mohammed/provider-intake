# T-008: The extractor transcribes; judgments become advisory issues

Status: in_review
Depends on: T-007

## Goal
A legible field is returned with its transcribed value and `status: found`, even when the model doubts the document's authenticity or the value's format; the doubt is surfaced as an issue code in the `issues` list (and so in the UI's Issues column) instead of nulling the value.

## Scope
In:
- `src/app/anthropic_adapters.py`: `EXTRACTION_PROMPT` instructs the model to transcribe what is present, not to judge authenticity or format validity, and to record any concern as a short snake_case issue code while leaving `status` as `found`.
- The prompt reserves `not_found` for a field absent from the document and `unreadable` for one it cannot read, and states that `invalid` is set only by deterministic validation, never by the model.
- `tests/test_T-008_transcribe_not_judge.py`.
- `docs/SPEC.md`: record the division of labour (model transcribes and observes; deterministic validation decides validity).
Out:
- Any change to `validate_field` / `validate_result` — the four deterministic codes (`empty_value`, `unknown_state`, `unparseable_date`, `expired`) and the downgrade-only invariant are unchanged.
- Any change to `FieldResult`, the A8 invariant, the response shape, or the UI (the Issues column already renders `issues`).
- Coercing a model-supplied `invalid` to some other status in `parse_extraction_json` — that would be our code *upgrading* certainty, which the constraints forbid. The prompt is the mechanism; this ticket does not police it in code.
- Rejecting or allow-listing model-invented issue codes; arbitrary strings stay preserved as-is.

## Interface
No signature changes. `EXTRACTION_PROMPT` (a module constant in `src/app/anthropic_adapters.py`) gains explicit instructions; `parse_extraction_json`, `validate_field` and the response shape are untouched.

Behaviour change, by example — a novelty licence whose `LICENSE#` reads `SARCASM`:

| | before (T-007) | after (T-008) |
|---|---|---|
| `value` | `null` | `"SARCASM"` |
| `status` | `invalid` | `found` |
| `raw` | `"SARCASM"` | `"SARCASM"` |
| `issues` | `["not_a_valid_format", "appears_fictional"]` | `["appears_fictional"]` |
| in `missing_fields` | yes | no |

An expired date is unaffected: deterministic validation still sets `invalid` + `expired` and nulls the value.

## Acceptance criteria
AC1. Given `EXTRACTION_PROMPT` When it is inspected Then it contains an instruction to transcribe rather than judge authenticity or format validity, an instruction to record concerns as issue codes while keeping `status` as `found`, and the statement that `invalid` is reserved for deterministic validation.
AC2. Given a stub client returning `{"license_number": {"value": "SARCASM", "status": "found", "raw": "SARCASM", "issues": ["appears_fictional"]}}` and the other three fields absent When `extract_fields(...)` is called Then `license_number.value == "SARCASM"`, `status == "found"`, `issues == ["appears_fictional"]`, and the field is not in `missing_fields`.
AC3. Given that same extractor result When it is passed through `validate_result(..., today=...)` Then `license_number` is returned unchanged — value, status and the model's issue code all survive, proving deterministic validation neither rejects the value nor strips advisory issues.
AC4. Given a stub result with `provider_name` `found` with `issues: ["low_contrast"]` and `expiration_date` `found` with value `"06-11-2015"` and `issues: ["appears_fictional"]` When validated with `today=date(2026, 9, 14)` Then `provider_name` stays `found` with its advisory issue, and `expiration_date` becomes `invalid` with `issues == ["appears_fictional", "expired"]`, value `None`, `raw` `"06-11-2015"` — advisory issues are preserved and deterministic codes are appended, not substituted.
AC5. Given a stub result where a field is genuinely absent (`status: "not_found"`) and another is illegible (`status: "unreadable"`) When extracted and validated Then both are returned unchanged with `value is None` and both appear in `missing_fields` — this ticket does not weaken the ability to report a field as missing or unreadable.

## Test plan
- File: `tests/test_T-008_transcribe_not_judge.py`. Stub client only; no network, no API key. Fixed `TODAY = date(2026, 9, 14)`.
- AC1: assert on the prompt text by keyword, not by exact wording, so the prompt can be reworded without breaking the suite; failure path: assert the prompt does **not** tell the model to mark suspicious documents invalid.
- AC2: happy path through `extract_fields` with the stub; edge: two advisory issues on one field both survive; failure path: a field the model omits entirely is still `not_found`.
- AC3: `validate_result` round trip; edge: an advisory issue on `state` survives normalization where the MODEL transcribed `value: "NJ"` with `raw: "Princeton, NJ 08540"` and `["inferred_from_address"]`; failure path: an address line supplied as the *value* still gets the deterministic `unknown_state` code appended.
  (Corrected during T-008: the original wording implied `normalize_state` turns `"Princeton, NJ 08540"` into `"NJ"`. It does not -- it resolves a two-letter code or a full state name only, so an address line returns `None`. Teaching it to parse addresses would be a separate ticket.)
- AC4: ordering and no-duplicate behaviour when advisory and deterministic codes combine.
- AC5: `not_found` / `unreadable` pass-through, and `missing_fields` still lists them.
- Note for the reviewer: AC1 asserts on prompt *content*, which cannot prove the live model obeys it. Whether the real model complies is verifiable only with an API key; record that limitation in the PR rather than implying the tests prove behaviour.
