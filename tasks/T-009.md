# T-009: The results table falls back to `raw` when `value` is null

Status: in_progress
Depends on: T-006

## Goal
A human looking at an expired licence sees the date that was on the document, not a dash — the Value cell falls back to the `raw` text whenever `value` is null, so nothing the document said is hidden from the reader.

## Scope
In:
- `src/app/static/index.html`: the Value cell renders `value` when present, otherwise `raw`, otherwise the existing em-dash placeholder. The fallback is visually distinguishable from a confirmed value so a reader is not misled into thinking it was accepted.
- `tests/test_T-009_raw_fallback.py`.
Out:
- Any change to the API, the response shape, `FieldResult`, the A8 invariant, `validate_field`, or the `missing_fields` list. **`value` stays null in the JSON** — this is a display fallback only.
- Changing which fields are reported as missing. An expired licence is still `invalid` and still in `missing_fields`.
- Styling beyond what is needed to mark the fallback as unconfirmed.

## Why
`FieldResult` nulls `value` whenever `status` is not `found` (SPEC A8), so an expired date, an
unparseable date and an unknown state all arrive with `value: null` and the real text in `raw`.
The page renders only `value`, so all three show an em dash and the reader has to guess what the
document actually said:

| field | value | status | issues | shown today | shown after |
|---|---|---|---|---|---|
| expiration_date | `null` | `invalid` | `["expired"]` | `—` | `06-11-2015` |
| state | `null` | `invalid` | `["unknown_state"]` | `—` | `Ontario` |
| license_number | `null` | `not_found` | `[]` | `—` | `—` (no raw either) |

## Interface
No Python signature changes and no API change. `src/app/static/index.html` only: the function that
fills `td[data-cell="value"]` gains the fallback, and the fallback is marked (e.g. a
`data-unconfirmed="true"` attribute on the cell plus a muted style) so tests and readers can tell
the two apart.

## Acceptance criteria
AC1. Given an extraction response where `expiration_date` has `value: null`, `raw: "06-11-2015"` and `status: "invalid"` When the page renders it Then the Value cell shows `06-11-2015`, the Status cell shows `invalid`, and the Issues cell shows `expired`.
AC2. Given a field with `value: null` and `raw: null` (nothing was read at all) When the page renders it Then the Value cell shows the existing em-dash placeholder and is not marked as a fallback.
AC3. Given a field with a confirmed `value` When the page renders it Then the Value cell shows `value`, `raw` is not displayed, and the cell is not marked as a fallback.
AC4. Given a field rendered from `raw` When the cell is inspected Then it carries the fallback marker (`data-unconfirmed="true"`), so a reader and a test can distinguish a transcription shown for context from a value the system accepted.
AC5. Given any of the above When the JSON response is inspected Then `value` is still null, the field is still listed in `missing_fields`, and no API behaviour changed — the fallback is presentation only.

## Test plan
- File: `tests/test_T-009_raw_fallback.py`.
- The page's JavaScript is not executed by the suite (T-006's known ceiling), so AC1–AC4 assert the served HTML/JS contract: the render function references `raw` as a fallback, and the fallback marker appears in the source. Say so in the module docstring rather than implying the rendering is proven.
- AC5 is a real endpoint test with a stub extractor: assert the JSON still has `value: null` and `missing_fields` unchanged, so a display change cannot quietly become an API change.
- Recommended, and the honest way to actually prove AC1–AC4: a jsdom-driven test, as the orchestrator used by hand during T-006. If that is out of scope here, record in the PR that the rendering itself is verified manually, not in CI.
- Fixtures: `create_app()` + `TestClient`; stub extractor for AC5. No network, no API key.
